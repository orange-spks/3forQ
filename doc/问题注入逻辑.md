# 问题注入逻辑

## 概述

3for 通过 `webview.executeJavaScript()` 将用户在顶部搜索栏输入的问题，注入到各个信息源页面的输入框中，并触发提交。整个逻辑位于 `src/renderer.js` 的 `buildFillScript()` 函数内。

注入流程分为四个阶段：

1. **确定源类型策略**：根据 `ALL_SOURCES[sourceId].type` 判断是否为 LLM 源。
2. **定位目标输入框**：通过源专属选择器或通用启发式找到正确的输入元素。
3. **填充问题文本**：模拟真实用户输入，触发各类事件保证 React 等框架能感知。
4. **触发提交**：优先点击发送/搜索按钮，否则模拟回车键。

---

## 1. 源类型与策略

`fillWebview()` 调用 `buildFillScript(query, { preferBottom, sourceId })` 时，`preferBottom` 由 `isLLMSource()` 决定：

```js
function isLLMSource(sourceId) {
  return (getSourceConfig(sourceId).type || '').includes('LLM');
}
```

### 1.1 源类型对照表

| 源 | type | 是否 LLM | 策略 |
|---|---|---|---|
| ChatGPT | `LLM` | ✅ | `preferBottom = true` |
| Doubao | `LLM` | ✅ | `preferBottom = true` |
| Kimi | `LLM/搜索` | ✅ | `preferBottom = true` |
| Gemini | `LLM` | ✅ | `preferBottom = true` |
| Grok | `LLM` | ✅ | `preferBottom = true` |
| 小红书 | `社区` | ❌ | `preferBottom = false` |
| 秘塔搜索 | `AI搜索` | ❌ | `preferBottom = false` |
| Bing | `搜索引擎` | ❌ | `preferBottom = false` |

`preferBottom` 决定了两套不同的输入框选择策略：LLM 源假设聊天 prompt 位于页面中下部，非 LLM 源假设搜索框位于页面顶部。

---

## 2. 输入框定位逻辑

### 2.1 Step 0：源专属选择器（仅 Grok）

Grok 的 prompt 输入框位于页面中部，且顶部/侧边存在「搜索已有对话」框，容易被通用启发式误填。因此为 Grok 单独维护一组特征选择器：

```js
[
  'textarea[placeholder*="你想知道什么"]',
  'textarea[aria-label*="向 Grok 提任何问题"]',
  'textarea[placeholder*="Ask anything"]',
  'textarea[aria-label*="Ask Grok anything"]',
]
```

命中条件：
- 元素可见（`el.offsetParent !== null`）
- 宽度大于 100px（`rect.width > 100`）
- 高度大于 0（`rect.height > 0`）

只要命中，直接作为目标输入框，跳过后续通用逻辑。

### 2.2 Step 1：通用候选扫描

#### 2.2.1 选择器列表

根据 `preferBottom` 使用不同的选择器：

```js
// LLM 源（preferBottom = true）
[
  'textarea',
  '[contenteditable="true"]',
  'div[role="textbox"]',
  'input[type="text"]',
  'input:not([type])',
]

// 非 LLM 源（preferBottom = false）
[
  'textarea',
  '[contenteditable="true"]',
  'div[role="textbox"]',
  'input[type="text"]',
  'input[type="search"]',
  'input:not([type])',
]
```

**关键区别**：LLM 源不包含 `input[type="search"]`，避免把问题填到「搜索已有对话」这类搜索框里。

#### 2.2.2 候选筛选

对每个匹配元素，收集满足以下条件的候选：

```js
rect.width > 100 && rect.height > 0 && el.offsetParent !== null
```

### 2.3 Step 2：候选排序与选择

#### 2.3.1 搜索框识别

```js
function isSearchLike(el) {
  const hint = (
    (el.getAttribute('placeholder') || '') + ' ' +
    (el.getAttribute('aria-label') || '') + ' ' +
    (el.textContent || '').trim().slice(0, 80)
  ).toLowerCase();
  return /search|搜索|查找/.test(hint);
}
```

只要 `placeholder`、`aria-label` 或文本内容里出现 `search`、`搜索`、`查找` 关键字，就视为搜索框。

#### 2.3.2 LLM 源选择策略

1. 从候选中排除搜索框，得到 `chatCandidates`。
2. 在 `chatCandidates` 中，优先保留位于页面中下部（`rect.top >= viewportHeight * 0.33`）的元素，得到 `lowerCandidates`。
3. 如果 `lowerCandidates` 非空，从中选择最靠下的元素（`rect.bottom` 最大）。
4. 否则从 `chatCandidates` 全部中选择最靠下的元素。

**阈值说明**：使用 `0.33` 而非 `0.5`，是为了覆盖 Grok 等将 prompt 放在页面中部的布局。

#### 2.3.3 非 LLM 源选择策略

直接取第一个可见候选：

```js
input = candidates[0].el;
```

因为非 LLM 源（搜索引擎、社区）的搜索框通常在页面顶部，按选择器优先级第一个命中的就是目标。

### 2.4 Step 3：兜底策略

如果前面的逻辑都没有找到输入框，依次尝试：

1. **放宽宽度限制**：宽度阈值从 100px 降到 50px，再次扫描。
2. **忽略可见性**：直接取 `document.querySelector('textarea')`、`[contenteditable="true"]`、`input[type="text"]`。

如果仍然找不到，返回 `{ filled: false, reason: 'no-input-found' }`。

## 3. 问题填充逻辑

找到目标输入框后，调用 `fillInput(input, query)` 进行填充。

### 3.1 React / 框架兼容赋值

对于普通 `input`/`textarea`，使用原生 setter 触发 React 的受控组件更新：

```js
function setNativeValue(el, value) {
  const proto = el.tagName === 'TEXTAREA'
    ? HTMLTextAreaElement.prototype
    : HTMLInputElement.prototype;
  const descriptor = Object.getOwnPropertyDescriptor(proto, 'value');
  if (descriptor && descriptor.set) {
    descriptor.set.call(el, value);
  } else {
    el.value = value;
  }
}
```

对于 `contenteditable` 或 `role="textbox"` 的元素，直接设置 `textContent`。

### 3.2 事件派发

填充后派发以下事件，确保各前端框架感知到输入变化：

- `input`（bubbles）
- `change`（bubbles）
- `compositionend`（bubbles）
- `beforeinput`（通过 `InputEvent`，bubbles、cancelable）

所有事件派发都经过 `safeDispatch` 包装，先检查事件构造函数是否存在，避免某些 webview 上下文缺失 API 导致崩溃。

---

## 4. 提交逻辑

填充完成 500ms 后，调用 `trySubmit(input)` 尝试提交问题。

### 4.1 发送按钮选择器

按优先级匹配常见的 send/submit 按钮：

```js
[
  'button[data-testid="send-button"]',
  'button[data-testid="fruitjuice-send-button"]',
  'button[aria-label*="Send"]',
  'button[aria-label*="发送"]',
  'button[aria-label*="提交"]',
  'button[aria-label*="Submit"]',
  'button[aria-label*="搜索"]',
  'button[aria-label*="search" i]',
  'button[aria-label*="send" i]',
  'button[class*="send" i]',
  'button[class*="submit" i]',
  'button[class*="search" i]',
  'button[type="submit"]',
  'button svg[class*="send" i]',
  'button svg[class*="arrow" i]',
]
```

### 4.2 附近按钮启发式

如果全局选择器没命中，在输入框的 `form` 或父元素内查找可见按钮，判断条件：
- 按钮文本或 `aria-label` 包含 `send`、`发送`、`搜索`、`submit`、`搜`
- 或者按钮内包含 `svg` 图标

### 4.3 回车键兜底

如果还是没有找到发送按钮，对输入框派发 `Enter` 键的 `keydown` 和 `keyup` 事件。

---

## 5. 错误处理

整个注入脚本被包裹在 `try-catch` 中：

```js
return `(() => {
  try {
    // 定位、填充、提交逻辑
  } catch (e) {
    return { filled: false, reason: 'exception', error: e.message, stack: e.stack };
  }
})()`;
```

这样即使 webview 内部抛出异常，`executeJavaScript()` 也会正常返回错误信息，而不是直接失败。`fillWebview()` 会重试最多 3 次。

---

## 6. 已知限制

- **Grok 是目前唯一有源专属选择器的源**，其他 LLM 源仍依赖位置和可见性启发式。
- 如果某个 LLM 源改了 prompt 输入框的位置（如放到页面顶部），`preferBottom` 策略可能失效。
- 搜索框识别依赖 `placeholder`、`aria-label` 和文本内容中的关键字，如果目标网站使用其他语言或无明显提示，可能误判。
- 非 LLM 源直接取第一个可见输入框，如果页面存在多个输入框（如筛选框、搜索框共存），可能填错。

---

## 7. 修改建议

当新增源或现有源出现填充位置错误时，可按以下顺序排查：

1. 检查该源的 `type` 是否设置正确，决定 `preferBottom`。
2. 对于 LLM 源，优先为其添加源专属选择器（参考 Grok），比启发式更稳定。
3. 调整 `viewportHeight * 0.33` 阈值，匹配 prompt 实际位置。
4. 调整 `isSearchLike` 的关键字列表，避免误过滤或误命中搜索框。
5. 修改后务必用 `vm.Script` 检查生成后的脚本语法，不能只做 `node --check`。
